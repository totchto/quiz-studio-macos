# Quiz Studio: обновление приложения из приложения

**Статус:** согласованная спецификация для подготовки технического плана
**Дата:** 2026-11-06

## Цель

Пользователи Quiz Studio должны получать новые версии без повторного ручного скачивания ZIP с GitHub. Распространение остаётся вне Mac App Store.

## Согласованные решения

- Использовать Sparkle для macOS.
- Проверять обновления автоматически при запуске и дать пользователю команду ручной проверки.
- Публиковать установочные ZIP и ленту обновлений (appcast) через GitHub Releases или другой статический HTTPS endpoint, связанный с релизным процессом проекта.
- Не устанавливать обновление без участия пользователя: показать доступную версию и заметки релиза, дать установить или отложить.
- Сохранить текущую поддержку macOS 14+ и Apple Silicon, пока отдельное решение не изменит эти требования.
- Не изменять формат `.quiz`, хранилище пользовательских данных или поведение игры в рамках этой функции.

## Текущее состояние и ограничения

- Приложение собирается как Swift Package Manager executable; `build.py` вручную формирует `.app` и ZIP.
- `Resources/Info.plist` задаёт bundle identifier `local.quizstudio.mac`, версию `0.20.0` и build `29`.
- Сейчас `.app` и вложенные исполняемые `yt-dlp`/`deno` подписываются ad hoc (`codesign --sign -`); нотариального заверения нет.
- Релизы распространяются ZIP-архивом через GitHub Releases.
- Установленные версии не содержат обновлятора, поэтому не могут сами получить Sparkle. Переход на первую версию с обновлением потребует от существующих пользователей один раз скачать и заменить приложение вручную. После этого обновления могут устанавливаться из приложения.

## Поведение пользователя

1. При запуске Sparkle выполняет автоматическую проверку с разумным интервалом (предлагаемый default — примерно раз в сутки, с учётом стандартного throttling Sparkle; не запрашивать сеть при каждом запуске).
2. Проверка не задерживает запуск, игру или работу редактора. При отсутствии сети, ошибке feed или отсутствии новой версии приложение продолжает работать; ошибка не должна повторяться навязчивыми диалогами.
3. В меню приложения доступна команда «Проверить обновления…». Она запускает проверку немедленно и даёт штатный результат Sparkle: версия найдена, обновлений нет либо проверка не удалась.
4. При наличии версии показать номер, заметки релиза и варианты установить сейчас/позже. Не выполнять тихое принудительное обновление и не перезапускать приложение без согласия.
5. Учитывать minimum OS/hardware и монотонно возрастающий `CFBundleVersion`, чтобы несовместимый пакет не предлагался подходящему пользователю.

## Требования к реализации

- Добавить Sparkle как зависимость SwiftPM и встроить нужный framework/служебные компоненты в итоговый `.app` корректным способом для кастомного `build.py`.
- Инициализировать updater один раз в lifecycle приложения; предоставить автоматическую и ручную проверку. Разместить ручную команду в привычном меню приложения; точное меню и локализацию уточнить при реализации по архитектуре SwiftUI/AppKit.
- Добавить в итоговый `Info.plist` настройки Sparkle (`SUFeedURL`, `SUPublicEDKey`) и сохранить существующие bundle identity/version fields. Feed URL должен быть постоянным HTTPS URL.
- Выпускать приложение с Developer ID Application code signing и нотариальным заверением Apple для внешнего распространения. Корректно подписывать вложенные Sparkle helpers и `yt-dlp`/`deno`; включить необходимые hardened-runtime entitlements только после проверки потребностей приложения.
- Подписывать архивы обновлений Sparkle EdDSA. Закрытый ключ хранить вне репозитория и релизных артефактов (предпочтительно в защищённом Keychain/секретах релизной среды); в приложение встраивать только открытый ключ.
- Настроить генерацию/публикацию appcast и ZIP как часть релиза. Существующая публичная загрузка ZIP должна продолжить работать. Изменение CI/release automation допускается только после проверки существующего процесса и его секретов.
- Обновить `build.py` и release-документацию; не создавать отдельную систему установки, не обновлять системные файлы и не трогать пользовательские quiz/bank/archive данные.

## Проверки и критерии приёмки

- Чистая Release-сборка формирует `.app` и ZIP с вложенным Sparkle, корректным `SUFeedURL`, public key, версией и bundle identifier.
- Проверка подписи проходит для приложения и вложенных компонентов; нотариальное заверение можно проверить Gatekeeper/notarytool.
- На старой Sparkle-enabled версии ручная команда обнаруживает новую совместимую версию, показывает заметки, позволяет отложить и успешно установить обновление.
- Проверка при запуске срабатывает по заданному интервалу и не мешает запуску приложения.
- Сценарии «обновлений нет», offline/feed недоступен, неподдерживаемая macOS/архитектура и повреждённая/неверно подписанная загрузка безопасно обрабатываются; неверная подпись никогда не устанавливается.
- Проверить апгрейд поверх копии из `/Applications`, пользовательские документы `.quiz`, локальный банк и архив игр; пользовательские данные остаются нетронутыми.
- Проверить миграционный путь отдельно: для текущих версий 0.20.0 без Sparkle дать пользователю понятную ссылку/инструкцию для разовой ручной установки.

## Вне объёма

- Mac App Store.
- Тихая принудительная установка обновлений.
- Перенос приложения на Intel или изменение минимальной версии macOS.
- Автоматическое обновление документов, банков вопросов или архива игр.
- Автоматическое удаление старых версий/пользовательских данных.

## Перед реализацией проверить

- Наличие активного Apple Developer Program и возможности выпустить Developer ID Application certificate и notarize app; это блокирует бесшовный надёжный релиз вне App Store, если сертификата ещё нет.
- Поддерживаемый текущей версией Sparkle способ интеграции в SwiftPM executable и упаковочный скрипт.
- Постоянный HTTPS адрес appcast и способ размещать feed/архивы через текущие GitHub Releases; проверить ограничения и поведение URL на реальных релизах.
- Уточнить место пункта меню и политику первого запуска, не меняя согласованное поведение auto + manual.
